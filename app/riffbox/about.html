Planned features

Not built yet, roughly in the order they look most useful. (The numbered phases further down are the committed build order; these are the extras that come after, or alongside, them.)

  • Serve this page's files from your website's htdocs folder (your preferred direction). Today the Python app hands out the page files along with the data. The plan: put the page files in /var/www/htdocs/ideas/ so your normal site tooling uploads them, and narrow the relayd rule so only /ideas/api/* goes to the app. The address stays /ideas/. Accepted trade-offs: two upload destinations, the page and the data code can get out of step if only one is uploaded, and the page files are no longer removed by the Riffbox-only uninstall.
  • Record-and-send Shortcut (Action Button, Back Tap or Lock Screen) that records and uploads directly, skipping the Voice Memos app.
  • Weekly email digest of a few forgotten hearted ideas, sent through your server's existing mail setup (smtpd and smtp2go), so no new service is needed.
  • Possible later: small waveform thumbnails in the list.

Context

The problem. Ideas were recorded as voice memos, then moved by hand into Obsidian and tagged. Because every step took effort, most ideas stayed buried in the Voice Memos app, and the ones that did get filed were hard to find later.

The goal. Make capture cost almost nothing: upload the recording and walk away, with no tagging required. Do the tagging later in a separate pass, in the Inbox. Then browse the Library the way you browse samples in a music plugin: filter by instrument, BPM, key and how interesting an idea is, and play anything immediately.

The approach. This lives on your own server, following Derek Sivers' Tech Independence guide: a small number of boring, well-understood tools, no outside services, and everything reversible. Rules you set along the way: no Cloudflare or other third-party hosting, manual tagging only (no AI), Obsidian is out of the workflow, the install must stay compartmentalised so it can be removed completely, and the build must go in small tested phases.

What the guide and ti.sh already gave us

Riffbox sits on top of the server the guide builds. These facts come from the guide, the ti.sh script, and the configuration files we read on your server in Phase 0.

  • The machine: OpenBSD 7.9 on a Vultr server with 1 CPU, 1 GB of memory and 25 GB of disk (about 18 GB was free when we checked). That is small, which is why nothing here runs heavy software, and why audio conversion happens one file at a time.
  • Your account: you log in with an SSH key only (passwords and root login are switched off), and your account can run doas (OpenBSD's sudo) without a password.
  • The web front door: relayd handles HTTPS on port 443 and decides where each request goes by host name and path. Your website's pages are handed out by httpd from /var/www/htdocs. acme-client gets the Let's Encrypt certificate, and a weekly cron job (Fridays, 03:11) renews it.
  • The firewall (pf) only lets in ports 22, 25, 80, 443, 587 and 993. Traffic on the server's own loopback address is unrestricted, which is why the app can listen privately on 127.0.0.1 and be reached only through relayd.
  • A precedent we copied: relayd already routes dav. to a Python program (Radicale) listening on loopback. Riffbox is wired in the same way.
  • The encrypted disk at /mnt only exists after you type m and enter its passphrase, and is gone after a reboot. Riffbox must run unattended, so none of its live data is kept there.
  • Mail: the server runs its own mail software and sends outgoing mail through smtp2go. The planned weekly digest would reuse this.
  • Software already present: the script installs curl, rsync, Radicale, links, mutt and dovecot. Python came along with Radicale. Riffbox added Flask, waitress and (for the FLAC copies and the waveforms) ffmpeg.

Architecture

What happens when you use it

Your browser asks for an address under /ideas over HTTPS. relayd notices the path and forwards the request to a small Python program (Flask, run by a server called waitress) listening on 127.0.0.1:8100. The program checks you are logged in, then reads or writes the database and the audio files. Everything else on your domain is still handled by httpd exactly as before.

Where each piece lives on the server

PieceLocationNotes
The route/etc/relayd.confThree added lines that send /ideas to the app. Nothing else of yours was changed.
The service/etc/rc.d/riffboxStarts at boot and runs as the _riffbox account, which has no shell, no login and no doas.
The code/usr/local/riffboxOwned by root, so the app cannot change its own code. Includes the page files (static/) and this page.
Secrets and settings/etc/riffbox.confSession key, upload token, login passphrase, address prefix and the ffmpeg path. Deploys never touch it.
Your data/var/riffboxThe SQLite database (riffbox.db) and the audio/ folder with your originals (and the FLAC play copies). A tmp/ folder inside it is scratch space for big uploads and exports, emptied at every start. Deploys never touch any of it.
Backup copy (optional)/var/riffbox-backupMade by the Back up now button or backup.py: the newest 14 database copies and a second copy of every original. Also your data, and on the same disk, so it does not protect against losing the server.
Optional helperffmpegMakes the FLAC copies and measures each recording's length and waveform. Without it the app still works, but there is no waveform or length, and Apple Lossless memos have no copy for Chrome.

Uploading and playing

  • Upload: the page sends each file along with its recorded time (the file's own timestamp) and an automatic title built from your local time. The server fingerprints the file (SHA-256) to refuse duplicates, stores it under a random name so file names can never collide or escape the folder, and puts it in the Inbox.
  • Apple Lossless memos: the server reads the file's own structure to see which codec it uses (no extra tool needed). If it is Apple Lossless, a single background worker converts it to FLAC (lossless in both directions; the tests compare the decoded audio sample for sample). The player uses the FLAC copy; Download always gives you the original, byte for byte.
  • Measuring: in the same background worker, ffmpeg decodes each upload to a small, quiet version of itself just long enough to find its length and draw 200 points of waveform. It is forced to read the file as the type its name says, so a file cannot pose as something else, such as a playlist pointing at other files. A file that cannot be measured is remembered, so it is not retried forever.
  • Playback: audio is served in ranges, which is what lets the browser jump to any point in a recording without downloading the whole thing.

Safety

  • One passphrase protects the app. The login cookie is signed, expires after 60 days, and is only sent to /ideas, never to the rest of your site.
  • After 5 wrong passphrases from one place, or 30 from anywhere, within 15 minutes, logins are refused until the oldest failure ages out. Restarting the service clears this.
  • A separate upload token can only add files. It cannot list, read or change anything.
  • This explanation page is only sent to a logged-in session; it is not part of the public page files.

How a new version gets onto the server

You download the new code, FreeFileSync copies it to a staging folder in your home directory, and one command on the server (sh ~/install-riffbox.sh) copies it into place and restarts the service. That staging step exists because FreeFileSync logs in as you and cannot write to root-owned folders.

Why it is built this way

  • A separate _riffbox account: this is the one program that accepts files from the internet. If a bug in it were ever exploited, the attacker would get an account that can do almost nothing, instead of yours, which has passwordless doas and is therefore effectively root. This is the same convention the guide uses for _radicale and _smtpd.
  • The page files live with the app, not in htdocs: this keeps one route, one folder to deploy, and a page that always matches its data code. It is a trade-off, and moving the page to htdocs is on the planned list above.
  • SQLite and plain files: no database server to run, and backing up means copying one folder.
  • Lossless copies, not lossy ones: the original is never altered, and the copy made for playback loses nothing.
  • Plain HTML, CSS and JavaScript, no build step: nothing to install or break, in the spirit of the guide. The page also has to avoid outside hosts and inline data, because the relayd security headers on your site forbid them.
  • Everything removable: deploy/UNINSTALL.md in the repository lists every change made to the server and how to reverse each one.

Tags

Two small tables: the list of tags (tags) and which tags each recording has (recording_tags). Nine tags come built in (bass, drums, keys, guitar, harmony, vocal, melody, rhythmic idea, full song), and you can add your own from the form, up to 100 in total. Names are lower-cased and tidied automatically, so "Beat BOX" and "beat box" are the same tag.

Files on disk

In /var/riffbox/audio/: your original upload under a random name (for example 3f9a….m4a), and, for Apple Lossless memos, a matching .flac playback copy under its own random name. Originals are never modified or deleted by the app.

Keeping your data portable

The goal: your recordings and everything you typed about them stay usable for decades, even if this app, this server or this code stops working. Two separate questions: what could stop the app, and how do you get the data out if it does.

What the app depends on

Depends onUsed forRisk over 20 years
SQLite (built into Python)All the details: titles, tags, notes, marks, dates. Very low. The file format is documented and stable, and the SQLite developers intend to support it through 2050.
Ordinary audio filesYour originals, untouched, in /var/riffbox/audio/. Very low for m4a, wav, mp3 and flac. Apple Lossless (ALAC) is open but some browsers can't play it, which is why a FLAC copy exists.
Python 3Runs the server. Low. Each new release removes a few old features, so the code is re-tested after each upgrade.
Flask and waitress (plus Werkzeug, Jinja2, MarkupSafe, itsdangerous, click, blinker) Web routing, login cookie, file upload parsing, the web server. The highest. Third-party code that changes between major versions, and whose OpenBSD package may eventually disappear. Mitigation: pinned versions, and a plan to keep copies of them (below).
ffmpeg (optional)Waveforms, lengths and FLAC play copies. Low impact. Without it everything still works; waveforms and play copies just stop being made.
OpenBSD, relayd, acme-client, your domain and VPSHosting and HTTPS. Ongoing cost and chores, but replaceable: the app is a plain Python program that can run on any computer, behind any web server.
A web browserThe interface: plain HTML, CSS and JavaScript, no frameworks and no build step. Low. It uses long-standing browser features only.

Not dependencies: Cloudflare or any other outside service, any JavaScript library, any font or file loaded from another site, any account anywhere.

What keeps it working for decades

  • The data matters more than the app. The app is small and replaceable; the SQLite file and the audio folder are what must survive. The most valuable habit is a regular export you can open without this app (next section).
  • Keep your own copy of the code and its libraries. The code is on GitHub, but keep a clone on your computer too, and add the exact pinned versions of Flask, waitress and their helpers (all pure Python, so one copy works on any computer) to that clone. Then nothing has to be downloaded to rebuild it.
  • Practice a restore. Once a year, start the app from a backup on an ordinary computer with only Python installed. If that works, you know the whole chain works. (Phase 8 builds this drill.)
  • Optional, later: remove Flask and waitress altogether, leaving only Python's standard library. The one hard part is reading file uploads, which Flask's helper Werkzeug does for us and which Python removed from its own library in 3.13; sending the file as a plain request body instead would avoid needing it. The test suite would show whether the rewritten version behaves identically. Not scheduled; worth doing if the libraries start to cause trouble.

Getting your data out today

The export script below does all of this for you. These two steps are the by-hand minimum, for a day when only Python is at hand. Do not copy riffbox.db with a plain file copy while the service runs: the newest changes can still be in a side file (riffbox.db-wal), so the copy would be missing them. This makes a consistent copy instead:

doas -u _riffbox python3 -c "import sqlite3; s = sqlite3.connect('/var/riffbox/riffbox.db'); s.backup(sqlite3.connect('/tmp/riffbox-copy.db'))"

Then copy /tmp/riffbox-copy.db and the whole /var/riffbox/audio/ folder to your computer (with your normal SFTP tool). Audio files have random names, so the audio alone tells you nothing: the titles, tags and notes live only in the database. To make a readable index, save this as dump.py and run python3 dump.py riffbox-copy.db > index.csv. The result opens in any spreadsheet and lists each recording's title, the file that holds it, dates, BPM, key, mark, song, notes and tags (it was checked against a database with quotes, commas and line breaks in the text):

import csv, sqlite3, sys
db = sqlite3.connect(sys.argv[1])
db.row_factory = sqlite3.Row
rows = db.execute("""SELECT r.id, r.title, r.filename AS file_on_disk, r.orig_filename, r.recorded_at,
  r.uploaded_at, r.status, r.bpm, r.key_root, r.key_mode, r.rating, r.used_in, r.notes,
  (SELECT group_concat(tag, '; ') FROM recording_tags WHERE recording_id = r.id) AS tags
  FROM recordings r WHERE r.deleted_at IS NULL ORDER BY r.recorded_at""").fetchall()
out = csv.writer(sys.stdout)
out.writerow(rows[0].keys() if rows else [])
for r in rows:
    out.writerow(list(r))

The export bundle

Open Backup and export (the link at the top of the app) and press Download the export (.zip). The zip is made as it downloads, so the server never has to store a second copy of your audio. The same export is also available from the command line: deploy/export.py needs only Python and does not use the app's web code, so it still works if the app or Flask is gone. Run it on the server, then fetch the result with your SFTP tool:

doas -u _riffbox python3 /usr/local/riffbox/deploy/export.py /var/riffbox /tmp/riffbox-export

It creates a folder with:

  • recordings/: each original audio file under a readable name such as 2026-03-01 Title [12].m4a, with a plain-text note beside it (2026-03-01 Title [12].md: the details at the top, your notes below). Any text editor opens it, and an Obsidian vault can open the folder as it is and play the audio inline.
  • index.html: every recording with its details and a play control. Double-click it; no server or software beyond a browser (checked, including with awkward characters in file names).
  • index.csv: the same list for a spreadsheet.
  • riffbox.db: the complete database as a copy, for full fidelity.
  • manifest-sha256.txt: a checksum for every file (sha256sum -c checks them). The export also compares each audio file with the checksum recorded when you uploaded it, and warns if one is damaged or missing.

Recordings in the Trash are left out unless you tick the box on the page (or add --include-trash). FLAC play copies are left out (they can be rebuilt from the originals). Other formats considered and not built: writing the details into the audio files' own tags (works for m4a, mp3 and flac, badly for wav) and a BagIt archive package (a library-world standard for exactly this purpose).

Backup and the practice restore

A backup keeps a consistent copy of the database (checked with SQLite's own integrity test, newest 14 kept) and a copy of every original audio file (copied once, never deleted). The Backup and export page shows the last backup, whether every audio file is covered, and has a Back up now button; deploy/backup.py does the same from the command line or a nightly schedule. Setup, the schedule and the restore drill are in deploy/PHASE8.md. There is deliberately no restore button.
